=====================================================================
  Developer's guide on protocol buffers (protoc, libprotobuf, protobuf)
=====================================================================

Last checked: 2026-09-26

This document describes where PRISM/T-PRISM uses protocol buffers, the
compatibility rules between the generated code and the runtime
libraries, the versions available in the common environments, and the
versions of protoc chosen for the code in this repository.


1.  Where protocol buffers are used
-----------------------------------

The schema is src/c/external/expl.proto (package prism).

C++ (src/c/up/tensor_preds.cpp, src/c/up/save_expl_graph.cpp) uses
protobuf only when compiled with USE_PB=1 (make -f Makefile.gmake
USE_PB=1).  The CMake build always compiles external/expl.pb.cc, but
does not define USE_PROTOBUF.

  predicate                         formats with USE_PB=1
  --------------------------------  ----------------------------------
  save_expl_graph/5                 json, pb, pbtxt
  save_flags/2,3 (also called by    json, pb, pbtxt
    save_expl_graph)
  save_placeholder_data/4,          pb (pbtxt is not supported)
    save_placeholder_goals/4

  json is written by protobuf (MessageToJsonString), pb by
  SerializeToOstream, and pbtxt by TextFormat::Print.

Without USE_PB (the default, and the packages built by the CI):
  - explanation graphs are written only in json (nlohmann/json); pb and
    pbtxt print "Unknown format." and write nothing,
  - flags are always written in json, even if pb or pbtxt is requested,
  - placeholder data in pb prints an error message.

Python (bin/tprism) uses the generated expl_pb2.py to parse the json
files with json_format.Parse: loader.load_explanation_graph (ExplGraph,
Option) and loader.load_input_json (PlaceholderData).  At present,
tprism does not read pb or pbtxt files.

The data formats themselves (pb wire format, text format, json) do not
depend on the versions: files written by PRISM linked with any
libprotobuf can be read by any Python protobuf runtime (checked: C++
3.12.4, 3.21.12, 36.2 x Python 4.21.12, 7.36.2).  Only the generated
code must match the runtime in each language.


2.  Compatibility rules
-----------------------

Version numbers: protoc 21.x = Python 4.21.x = C++ 3.21.x; protoc
22-25 = Python/C++ 4.x; 26-29 = 5.x; 30-33 = 6.x; 34- = 7.x.

C++:
  The generated code (expl.pb.cc, expl.pb.h) must be generated by the
  same version of protoc as the libprotobuf headers.  Otherwise the
  compilation stops with one of:

    #error This file was generated by a newer version of protoc which is
    #error This file was generated by an older version of protoc which is
    #error "Protobuf C++ gencode is built with an incompatible version of"

  (3.x checks the minor version; v26 and later check the exact version.)
  protobuf 22 and later require C++17 (abseil).

Python:
  - protoc <= 3.18 (e.g. the old expl_pb2.py generated by protoc 3.6):
    the code creates descriptors directly, which fails on runtime 4.21
    and later: "TypeError: Descriptors cannot be created directly."
  - protoc 3.20.0 - 26.x: the code works on every runtime from 3.20 to
    the latest 7.36 (tested).  Officially, "all generated code since
    3.20.0 will be supported until at least 8.x.y" (Cross-Version
    Runtime Guarantee, since runtime 6.32.0).
  - protoc 27 and later: the code calls ValidateProtobufRuntimeVersion
    and requires a runtime of the same or newer version (the
    runtime_version module does not exist in 5.26 and older).
  - Independently of the generated code, the pip wheels of protobuf
    older than 5.27.0 do not work on Python 3.14:
    "TypeError: Metaclasses with custom tp_new are not supported."

4.  Chosen versions
-------------------

Python (bin/tprism/expl_pb2.py, expl_pb2.pyi): protoc 3.21.12 (release
v21.12).  Runtime requirement: protobuf >= 4.21.12 (>= 5.27.0 on
Python 3.14 or later; see bin/requirements.txt).

  - No generated code works both on 3.12.4 (Ubuntu 22.04's
    python3-protobuf) and on 4.21 and later within the official
    guarantee, so python3-protobuf of Ubuntu 22.04 is not supported
    (install protobuf with pip there).  The next oldest runtime is
    4.21.12 (Ubuntu 24.04/26.04, MacPorts).
  - The code generated by protoc 21.12 has the same version as that
    runtime, and is supported from 4.21.12 to at least 8.x.  It also
    works on the runtimes of Colab (6.33.6, 7.36.1) and the latest
    (7.36.2).
  - protoc 3.21.12 is the protoc of Ubuntu 24.04/26.04 and Colab (apt
    install protobuf-compiler), so the code can be regenerated easily.
  - protoc 21.12 supports --pyi_out, so mypy-protobuf is not needed.
  - Alternatives: 3.20.3 lowers the official minimum runtime to 3.20,
    but no environment ships it anymore.  3.19.6 also works on Ubuntu
    22.04's python3-protobuf (C++ implementation only), but it is
    outside the official guarantee.  27 and later raise the minimum
    runtime to their own version (34 and later do not work on Colab's
    6.33.6).

C++ (src/c/external/expl.pb.cc, expl.pb.h): protoc 3.21.12.

  - No version is compatible with other libprotobuf versions (see 5.2).
  - 3.21.12 is the libprotobuf of the most common environments: Ubuntu
    24.04/26.04, Colab and MacPorts.
  - The generated code is included in the repository, so that PRISM
    can be compiled in environments without protoc.  The Makefiles do
    NOT regenerate it automatically.  With another version of
    libprotobuf (e.g. 3.12.4 in Ubuntu 22.04, 36.x in Homebrew), run
    `sh src/c/external/generate.sh` before compiling (src/c/README).

Compiler options (Makefile.opts.gmake, CMakeLists.txt): C++ sources
are compiled with -std=c++17 (required by protobuf >= 22), and C
sources with -std=gnu11 (gcc >= 15 defaults to C23, where `false` and
`true` in core/stuff.h are keywords).  The C++ sources do not use
`using namespace google::protobuf`, because google::protobuf::json
(protobuf >= 22) conflicts with nlohmann::json.

6.  How to regenerate the code
------------------------------

After changing expl.proto, regenerate both.

C++ (for the libprotobuf you link against; protoc must have the same
version):

    sh src/c/external/generate.sh

  The code in the repository should be kept as generated by protoc
  3.21.12.

Python (protoc 3.21.12 is required; generate.sh refuses other
versions):

    PROTOC=/path/to/protoc sh src/c/external/generate.sh python

  This writes bin/tprism/expl_pb2.py and expl_pb2.pyi.  protoc 3.21.12
  is `apt install protobuf-compiler` on Ubuntu 24.04/26.04, or the
  release binary:
  https://github.com/protocolbuffers/protobuf/releases/download/v21.12/protoc-21.12-linux-x86_64.zip

  pdoc (bin/tprism_docs) warns "Error parsing type stubs for
  tprism.expl_pb2" (NameError: name 'SwType' is not defined).  This is
  harmless.  pdoc executes .pyi files as Python code, which the stubs
  generated by protoc (any version) do not support: they refer to
  SwType before its definition, and declare the enum with
  metaclass=EnumTypeWrapper, which is valid only for type checkers
  (with `from __future__ import annotations`, pdoc fails at the latter
  with "TypeError: metaclass conflict").  pdoc then documents the
  runtime module instead, and the generated page is the same.  The
  stub from mypy-protobuf used before also caused this warning
  (_EnumTypeWrapper).  Type checkers (checked with mypy) accept the
  stub.


7.  When to revisit
-------------------

  - When the libprotobuf of the most common environments moves from
    3.21.12 (Ubuntu, Colab): regenerate the bundled C++ code.
  - Before protobuf 9.x: the guarantee for generated code since 3.20.0
    covers runtimes until at least 8.x.
  - Ubuntu 22.04 ends standard support in 2027-05.
  - Homebrew protobuf@33 is scheduled to be deprecated on 2027-03-31.
  - Colab's base OS or Python version changes: runs-on of
    .github/workflows/release4colab.yml should follow the base OS.
